# 3일차 프로젝트 뜯어보기

## 1. 디렉터리 역할

FastAPI 백엔드는 "요청이 들어와서 → 데이터가 처리되고 → 응답이 나가기"까지 여러 층(layer)으로 나눠서 관리한다. 각 폴더가 그 층 하나씩을 담당한다.

### `app/core/`
프로젝트 전역에서 공통으로 쓰는 설정/기반 코드를 모아두는 곳.
- `app/core/config.py`: `.env` 파일의 환경변수를 읽어오는 설정 클래스
- `app/core/db/databases.py`: DB 접속 주소 구성, 비동기 엔진/세션 생성, 모델의 부모 클래스인 `Base` 정의
- `app/core/db/models.py`: 여러 모델에서 공통으로 재사용하는 믹스인(`TimestampMixin` 등)

### `app/models/`
DB 테이블 구조를 SQLAlchemy 클래스로 정의하는 곳. 테이블 하나 = 클래스 하나 = 파일 하나로 관리한다.
- 예: `user.py`(`users` 테이블), `patient.py`(`patients` 테이블), `medical_record.py`, `xray_image.py`, `ai_analysis_result.py`
- `__init__.py`에서 모든 모델 클래스를 import해줘야 Alembic이 모델을 인식하고 마이그레이션에 반영할 수 있다.

### `app/schemas/`
API가 주고받는 데이터의 "모양"을 Pydantic `BaseModel`로 정의하는 곳. `app/models/`가 **DB 안의 모양**이라면, `app/schemas/`는 **API 요청/응답의 모양**이다. 예를 들어 회원가입 요청 body(비밀번호 포함)와 회원 정보 응답(비밀번호 제외)은 모양이 다르므로 스키마를 따로 만든다.

### `app/repositories/`
DB에 직접 쿼리를 날리는 함수들을 모아두는 곳 (예: `get_user_by_email(db, email)`, `create_patient(db, data)`). "DB 접근 로직"만 여기에 모아두면, 나중에 같은 조회 로직을 여러 API에서 재사용하기 쉽다.

### `app/services/`
비즈니스 로직(규칙)을 처리하는 곳. 예: 비밀번호 해싱, JWT 토큰 발급, "동일 이미지로 이미 예측한 적 있으면 캐시된 결과 반환" 같은 판단 로직. repositories가 "DB에서 가져오기/저장하기"만 한다면, services는 "그 데이터를 가지고 어떤 규칙을 적용할지"를 담당한다.

### `app/apis/`
실제 API 엔드포인트(`@router.get(...)`, `@router.post(...)`)를 정의하는 곳. 요청을 받아서 스키마로 검증하고, services를 호출해서 처리한 뒤, 결과를 응답으로 돌려준다. 여러 도메인별로 파일을 나눠서 작성하고(`user_apis.py`, `patient_apis.py` 등), 각각 `APIRouter`로 만든 뒤 `app/main.py`에 등록한다.

**정리하면 요청이 처리되는 순서**: `apis`(요청 받음) → `schemas`(검증) → `services`(규칙 적용) → `repositories`(DB 조회/저장) → `models`(실제 테이블) 순으로 안쪽까지 내려갔다가, 다시 바깥쪽으로 응답이 나간다.

## 2. 주요 파일 역할

### `app/main.py`
FastAPI 애플리케이션의 진입점(entry point). `app = FastAPI()`로 앱 객체를 만들고, `static`/`media` 폴더를 마운트하고, 각 도메인의 `APIRouter`를 `app.include_router(...)`로 등록한다. 서버를 실행하면(`uvicorn app.main:app`) 가장 먼저 실행되는 파일.

주의할 점: 파일 맨 아래 `@app.get("/{path:path}")` 캐치올(catch-all) 라우트가 있어서, 새 라우터는 **반드시 이보다 먼저 등록**해야 한다. 그렇지 않으면 캐치올이 먼저 요청을 가로챈다.

### `app/core/config.py`
`.env` 파일에 적어둔 환경변수(`DB_HOST`, `DB_PASSWORD` 등)를 파이썬 객체로 읽어오는 `Settings` 클래스. `pydantic-settings`를 사용해서, `.env`가 바뀌면 코드 수정 없이 값만 바뀐다. DB 접속 정보처럼 사람마다 다르거나 노출되면 안 되는 값들을 여기서 관리한다.

### `pyproject.toml`
이 프로젝트가 어떤 외부 라이브러리(의존성)를 쓰는지 적어둔 설정 파일. `fastapi`, `sqlalchemy`, `alembic`, `asyncmy` 등이 여기 명시되어 있다. `uv sync` 실행 시 이 파일을 보고 필요한 패키지들을 설치한다. Python 버전 요구사항(`requires-python = ">=3.13"`)도 여기 있다.

### `uv.lock`
`pyproject.toml`에 적힌 패키지들의 **정확한 버전**을 고정해두는 파일. `pyproject.toml`이 "fastapi 쓸 거야" 정도라면, `uv.lock`은 "fastapi 0.135.3 정확히 이 버전 쓸 거야"까지 못박아둔다. 이 파일 덕분에 팀원 전체가 `uv sync`만 하면 동일한 버전의 라이브러리 환경을 갖추게 되어, "내 컴퓨터에서는 되는데 남의 컴퓨터에서는 안 되는" 문제를 방지한다. 직접 수정하지 않고 `uv add`/`uv sync` 명령으로만 자동 갱신한다.

## 3. 데이터베이스 연결 설정 (`app/core/db/databases.py`)

```python
DATABASE_PREFIX = "mysql+asyncmy://"
DATABASE_URI = f"{settings.DB_USER}:{settings.DB_PASSWORD}@{settings.DB_HOST}:{settings.DB_PORT}/{settings.DB_NAME}"
DATABASE_URL = f"{DATABASE_PREFIX}{DATABASE_URI}"

async_engine = create_async_engine(DATABASE_URL, echo=False, future=True)
AsyncSessionLocal = async_sessionmaker(bind=async_engine, autoflush=False, expire_on_commit=False)
Base = declarative_base()

async def async_get_db() -> AsyncGenerator[AsyncSession, None]:
    async with AsyncSessionLocal() as db:
        yield db
```

- **`DATABASE_URL`**: `config.py`에서 읽어온 값들을 조합해서 만드는 실제 DB 접속 주소. 우리 프로젝트는 `mysql+asyncmy`(비동기 MySQL 드라이버)를 사용한다.
- **`async_engine`**: 이 주소로 실제 DB와 통신하는 연결 엔진.
- **`AsyncSessionLocal`**: 요청 하나당 하나씩 만들어지는 "DB와의 대화 세션".
- **`Base`**: 모든 모델 클래스가 상속받아야 하는 부모 클래스. `class User(Base):`처럼 써야 SQLAlchemy가 "이건 테이블로 만들 클래스구나"라고 인식한다.
- **`async_get_db()`**: API 함수에서 `Depends(async_get_db)`로 주입받아 사용하는, DB 세션을 빌려주고 끝나면 반납하는 함수.

## 4. SQLAlchemy 모델 작성 + Alembic 마이그레이션 방법

1. **ERD 확인** — [ERD 링크](https://dbdiagram.io/d/ai_health_assignment-69d5f55f808962968443c041)를 기준으로 테이블/컬럼/관계를 파악한다.
2. **모델 클래스 작성** — `app/models/`에 테이블별로 파일을 만들고, `Base`를 상속받는 클래스를 작성한다. 컬럼 타입, 제약조건(`nullable`, `unique` 등), 외래키(`ForeignKey`), 관계(`relationship`)까지 반영한다.
3. **`app/models/__init__.py`에 등록** — 작성한 모델 클래스를 전부 import해야, Alembic이 "이런 테이블들이 정의되어 있다"는 걸 인식할 수 있다.
4. **마이그레이션 파일 생성**
   ```bash
   alembic revision --autogenerate -m "설명"
   ```
   현재 모델 코드와 실제 DB 상태를 비교해서, 차이를 반영하는 마이그레이션 파일을 `alembic/versions/`에 자동 생성한다. 파일 안에는 `upgrade()`(적용할 변경사항)와 `downgrade()`(되돌리는 방법)가 들어있다.
5. **DB에 실제 적용**
   ```bash
   alembic upgrade head
   ```
   생성된 마이그레이션 파일의 `upgrade()` 내용을 실제 MySQL에 실행해서, 진짜 테이블을 만든다. 이 명령을 실행하기 전까지는 DB에 아무 변화도 없다 (모델 클래스는 어디까지나 "설계도"일 뿐).
6. **확인** — DB Viewer(또는 `mysql` 클라이언트)로 접속해서 테이블이 실제로 생성됐는지 확인한다.

되돌리고 싶을 땐 `alembic downgrade -1`로 마지막 변경을 취소할 수 있다.

## 5. API 구현 흐름

기능 하나(예: 회원가입)를 실제로 구현할 때 거치는 순서:

1. **모델 확인** — 이미 만들어진 `app/models/user.py`에 필요한 컬럼이 다 있는지 확인 (없으면 모델부터 추가하고 마이그레이션)
2. **스키마 작성** (`app/schemas/`) — 요청 body 모양(`UserSignupRequest`)과 응답 모양(`UserResponse`)을 Pydantic으로 정의. 여기서 유효성 검증 규칙(비밀번호 정규식, 이메일 형식 등)도 함께 작성
3. **레포지토리 작성** (`app/repositories/`) — `create_user(db, data)`처럼 실제 DB에 저장/조회하는 함수 작성
4. **서비스 작성** (`app/services/`) — 비밀번호 해싱, 중복 이메일 체크 같은 규칙을 처리한 뒤 레포지토리 호출
5. **API 라우터 작성** (`app/apis/`) — `@router.post("/signup")`로 엔드포인트를 만들고, 스키마로 요청을 받아 서비스를 호출, 결과를 응답 스키마로 반환
6. **`main.py`에 라우터 등록** — `app.include_router(...)`로 합체 (캐치올 라우트보다 먼저 등록)
7. **Swagger UI(`/docs`)에서 테스트** — 정상 케이스와 예외 케이스(잘못된 입력, 중복 이메일 등) 모두 확인
8. **프론트엔드 연동 확인** — `static/apis.js`가 기대하는 엔드포인트/요청·응답 형식과 일치하는지 대조 후, 실제 화면에서 동작 확인

이 8단계는 User뿐 아니라 환자, 진료기록, AI예측 등 다른 도메인에도 동일하게 반복 적용된다.
