# 3일차. 프로젝트 템플릿 뜯어보기

Stage 3 - "프로젝트 템플릿 뜯어보기" 과제로 작성한 문서입니다. 클론받은 `AH_health_web_development_assignment` 템플릿의 디렉터리/파일 구조와, 그 위에 SQLAlchemy + Alembic으로 DB 모델/마이그레이션을 만드는 전체 흐름을 정리합니다.

## 1. 각 디렉터리는 어떤 역할을 수행하는가

FastAPI 프로젝트를 계층별로 나눈 구조로, 각 디렉터리는 아래와 같은 책임을 가집니다. (참고: [FastAPI 프로젝트의 결합도 낮추기 전략](https://devocean.sk.com/blog/techBoardDetail.do?ID=166993&boardType=techBlog), [Structuring a FastAPI Project: Best Practices](https://dev.to/mohammad222pr/structuring-a-fastapi-project-best-practices-53l6))

- **`app/core/`** : 앱 전역에서 쓰이는 설정, 상수, DB 연결 등 "기반 인프라" 코드를 모아두는 곳입니다. `config.py`(환경변수 기반 설정), `db/`(엔진·세션·Base 선언) 등이 위치합니다. 특정 도메인 로직에 속하지 않는, 프로젝트 전체가 공유하는 코드입니다.
- **`app/models/`** : SQLAlchemy ORM 모델(테이블 정의)을 모아두는 곳입니다. 실제 DB 테이블 하나당 클래스 하나를 대응시켜 작성합니다. (`user.py`, `patient.py`, `medical_record.py`, `xray_image.py`, `ai_analysis_result.py`)
- **`app/repositories/`** : DB에 직접 접근하는 쿼리(CRUD) 코드를 모아두는 계층입니다. "어떤 데이터를 어떻게 가져오고 저장할지"만 책임지고, 비즈니스 로직은 포함하지 않습니다. Service 계층이 Repository를 호출해서 데이터를 가져오는 구조입니다.
- **`app/schemas/`** : Pydantic 모델(요청/응답 스키마)을 모아두는 곳입니다. API의 입력값 검증(Request Body)과 출력 형태(Response Model)를 정의합니다. SQLAlchemy 모델(DB 구조)과 Pydantic 스키마(API 입출력 형태)는 서로 다른 목적을 가지므로 분리합니다.
- **`app/services/`** : 실제 비즈니스 로직을 담당하는 계층입니다. 여러 Repository를 조합하거나, 도메인 규칙(예: "관리자만 삭제 가능")을 적용하는 코드가 위치합니다. API 계층은 Service를 호출하기만 하고, Service는 Repository를 통해 데이터를 다룹니다.
- **`app/apis/`** : FastAPI `APIRouter`로 실제 엔드포인트(`@router.get`, `@router.post` 등)를 정의하는 곳입니다. 요청을 받아 Schema로 검증하고, Service를 호출한 뒤 결과를 반환하는 얇은 계층(Presentation Layer)입니다.

이렇게 계층을 나누는 이유는 **결합도를 낮추기 위함**입니다. 예를 들어 DB를 MySQL에서 다른 DB로 바꾸더라도 `models`/`repositories`만 수정하면 되고, `services`/`apis`는 영향을 받지 않도록 설계할 수 있습니다.

### 요청 흐름 요약

```
Client 요청
  → app/apis/*.py       (라우팅, Pydantic 스키마로 요청 검증)
    → app/services/*.py (비즈니스 로직)
      → app/repositories/*.py (DB 쿼리 실행)
        → app/models/*.py     (SQLAlchemy 테이블 정의)
          → MySQL DB
```

## 2. 각 파일의 역할

- **`app/main.py`** : FastAPI 앱(`FastAPI()`)의 진입점입니다. `static`/`media` 폴더를 정적 파일 서빙용으로 마운트하고, `app/apis/`에 정의된 라우터들을 `app.include_router(...)`로 등록합니다. `/healthcheck`(헬스체크), `/`(SPA index 반환), 그리고 API/정적 경로가 아닌 나머지 경로를 프론트엔드 SPA로 라우팅해주는 `catch_all`도 여기 있습니다.
- **`app/core/config.py`** : `pydantic-settings`의 `BaseSettings`를 상속한 `Settings` 클래스입니다. `.env` 파일(`model_config`의 `env_file`)에서 `DB_USER`, `DB_PASSWORD`, `DB_HOST`, `DB_PORT`, `DB_NAME` 같은 환경변수를 읽어와 코드 어디서든 `settings.DB_HOST`처럼 타입 안전하게 접근할 수 있게 해줍니다. 비밀번호 같은 값을 코드에 하드코딩하지 않기 위한 장치입니다.
- **`pyproject.toml`** : 프로젝트 메타데이터(`name`, `version`, `requires-python`)와 의존성 목록(`dependencies`)을 정의하는 `uv`/PEP 621 표준 설정 파일입니다. `alembic`, `fastapi`, `sqlalchemy`, `asyncmy`(MySQL 비동기 드라이버) 등이 명시돼 있습니다.
- **`uv.lock`** : `pyproject.toml`에 명시된 의존성들의 **정확한 버전**과 하위 의존성까지 고정(lock)해둔 파일입니다. 팀원 전체가 `uv sync` 한 번으로 완전히 동일한 패키지 버전 조합을 재현할 수 있게 해주는, 재현 가능한 빌드를 위한 파일입니다. 사람이 직접 수정하지 않고 `uv add`/`uv sync`로만 갱신합니다.

## 3. 데이터베이스 연결 설정 — `app/core/db/databases.py`

```python
DATABASE_PREFIX = "mysql+asyncmy://"
DATABASE_URI = f"{settings.DB_USER}:{settings.DB_PASSWORD}@{settings.DB_HOST}:{settings.DB_PORT}/{settings.DB_NAME}"
DATABASE_URL = f"{DATABASE_PREFIX}{DATABASE_URI}"

async_engine = create_async_engine(DATABASE_URL, echo=False, future=True)
AsyncSessionLocal = async_sessionmaker(bind=async_engine, autoflush=False, expire_on_commit=False)
Base = declarative_base()

async def async_get_db() -> AsyncGenerator[AsyncSession, None]:
    async with AsyncSessionLocal() as db:
        yield db
```

- `mysql+asyncmy://` : SQLAlchemy가 MySQL에 **비동기**로 접속할 때 `asyncmy` 드라이버를 사용하도록 지정하는 접속 문자열 prefix입니다. FastAPI가 비동기 프레임워크이므로, DB 드라이버도 비동기(asyncmy)를 사용해야 이벤트 루프를 막지 않습니다.
- `async_engine` : 실제 DB와의 커넥션 풀을 관리하는 SQLAlchemy 엔진입니다.
- `AsyncSessionLocal` : 요청마다 새로운 비동기 세션(Session, 즉 하나의 "작업 단위")을 만들어주는 팩토리입니다.
- `Base` : 모든 ORM 모델(`app/models/*.py`)이 상속받는 선언적 베이스 클래스입니다. `Base.metadata`에 등록된 테이블 정의들을 Alembic이 읽어서 마이그레이션에 활용합니다.
- `async_get_db()` : FastAPI의 `Depends()`로 라우터에 주입해서 쓰는 세션 제너레이터입니다. `async with`로 세션을 열고, 요청 처리가 끝나면 자동으로 세션을 정리합니다.

## 4. SQLAlchemy로 모델을 작성하고 Alembic으로 마이그레이션하는 방법

### 4-1. 모델 작성 (`app/models/*.py`)

SQLAlchemy 2.0 스타일(`Mapped[]`, `mapped_column()`)로 테이블을 정의합니다. 예:

```python
class Patient(Base):
    __tablename__ = "patients"

    id: Mapped[int] = mapped_column(BigInteger, primary_key=True, autoincrement=True)
    name: Mapped[str] = mapped_column(String(30), nullable=False)
    ...
```

- 클래스가 `Base`를 상속하고 `__tablename__`을 지정하면, `Base.metadata`에 테이블 정의가 자동으로 등록됩니다.
- `ForeignKey("patients.id")`로 다른 테이블을 참조하고, `relationship()`으로 ORM 레벨에서 객체 간 관계(1:N 등)를 연결합니다.

새로 만든 모델은 반드시 **`app/models/__init__.py`에서 import**해야 합니다. Alembic의 `alembic/env.py`가 `from app import models`로 패키지를 통째로 import하기 때문에, `__init__.py`에 등록되지 않은 모델은 `Base.metadata`에 잡히지 않아 마이그레이션 대상에서 누락됩니다.

### 4-2. 마이그레이션 파일 생성 (autogenerate)

```bash
uv run alembic revision --autogenerate -m "add users, patients, medical_records, xray_images, ai_analysis_results tables"
```

- Alembic이 `alembic/env.py`에 설정된 `target_metadata`(=`Base.metadata`, 즉 코드로 작성한 모델들)와 **현재 연결된 실제 DB의 스키마**를 비교(diff)합니다.
- 차이가 나는 부분(테이블 추가/삭제, 컬럼 변경 등)을 감지해서 `alembic/versions/`에 새 리비전 파일을 자동 생성합니다. 파일 안의 `upgrade()`/`downgrade()` 함수에 실제로 실행할 DDL(`op.create_table`, `op.add_column` 등)이 채워집니다.
- **autogenerate는 100% 정확하지 않을 수 있으므로**, 생성된 파일은 항상 열어서 의도한 대로 만들어졌는지 검토·수정해야 합니다.

### 4-3. DB에 실제로 반영 (upgrade)

```bash
uv run alembic upgrade head
```

- 현재 DB에 기록된 리비전(alembic이 `alembic_version` 테이블에 저장)을 기준으로, 아직 적용되지 않은 리비전들을 순서대로 실행해서 최신(`head`) 상태까지 스키마를 맞춥니다.
- 잘못 적용했을 때는 `uv run alembic downgrade -1`로 직전 리비전으로 되돌릴 수 있습니다.

### 4-4. 전체 흐름 요약

```
1) app/models/*.py 에 SQLAlchemy 모델 작성
2) app/models/__init__.py 에 새 모델 import 추가
3) alembic revision --autogenerate -m "설명"  → 리비전 파일 생성 (diff 기반)
4) 생성된 리비전 파일 검토/수정
5) alembic upgrade head  → 실제 DB에 스키마 반영
```

## 5. API 구현 흐름

`app/apis/practice_apis.py`(1~2일차 연습용 API)를 예로 보면, FastAPI에서 하나의 API 엔드포인트는 대략 다음 흐름으로 동작합니다.

1. **라우터 정의** : `router = APIRouter(prefix="/practice_api", tags=["practice"])` 로 이 파일의 엔드포인트들을 하나의 그룹으로 묶고, `app/main.py`에서 `app.include_router(router)`로 앱에 등록합니다.
2. **요청 스키마 검증** : `class UserCreate(BaseModel)`처럼 Pydantic 모델로 요청 바디의 형태·제약조건(`Field(min_length=...)`)을 선언하면, FastAPI가 요청이 들어올 때 자동으로 검증하고 실패 시 422 에러를 반환합니다. `@field_validator`로 이메일 형식, 비밀번호 규칙 같은 커스텀 검증도 추가할 수 있습니다.
3. **경로 함수(엔드포인트) 실행** : `@router.get("/users")`, `@router.post("/users")`처럼 HTTP 메서드 + 경로에 매핑된 함수가 실제 요청을 처리합니다. 지금은 메모리 리스트(`user_list`)를 직접 다루고 있지만, 실제 서비스 구조에서는 이 자리에서 **Service → Repository → Model(DB)** 순서로 호출해 실제 DB 데이터를 다루게 됩니다.
4. **응답 반환** : 함수의 반환값(dict, list 등)을 FastAPI가 자동으로 JSON으로 직렬화해서 응답합니다. 존재하지 않는 리소스 등 예외 상황은 `HTTPException(status_code=..., detail=...)`을 raise해서 적절한 HTTP 상태코드로 응답합니다.
5. **자동 문서화** : 이렇게 타입 힌트 + Pydantic 스키마로 작성된 API는 FastAPI가 자동으로 OpenAPI 스펙과 `/docs`(Swagger UI) 문서를 생성해줍니다.

정리하면, 지금 `practice_apis.py`는 계층 분리 없이 라우터 안에 모든 로직이 있는 "연습용" 코드이고, 앞으로 실제 도메인(환자/진료기록/X-Ray/AI 분석)을 구현할 때는 이 로직을 `apis → services → repositories → models`로 나누어 작성하게 됩니다.
