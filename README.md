# AI Health Web Assignment

흉부 X-Ray 이미지 기반 폐렴 판독 AI 모델을 활용한 환자 관리 백오피스입니다. FastAPI + SQLAlchemy(async) + MySQL을 기반으로 환자/진료기록을 관리하고, Redis 큐로 분리된 AI 워커가 폐렴 예측을 수행합니다.

## 프로젝트 진행 과정 총정리

과제 기간(2026-08-24 ~ 2026-09-08) 동안 팀이 실제로 어떤 순서로, 어떤 방식으로 이 프로젝트를 만들어왔는지 단계별로 정리합니다.

### 1. Team Rule 정의

첫 미팅에서 [`docs/1일차_team_rules.md`](docs/1일차_team_rules.md)에 최소한의 팀 규칙(참여 시간, 집중 원칙)을 정했습니다. 다만 "누가 어떤 도메인을 담당할지"에 대한 역할 분담까지는 이 시점에 명확히 합의되지 않았고, 이는 이후 3~5일차에 같은 API를 여러 팀원이 중복으로 구현하는 시행착오로 이어졌습니다. 이 경험을 통해 초기 팀 규칙에는 시간·태도뿐 아니라 **작업 배정 방식과 담당자 확인 절차**까지 포함되어야 한다는 걸 배웠습니다.

### 2. 사용자 요구사항 정의

이번 과제에서는 팀이 요구사항 정의서(REQ-USER/PTNT/MDR/PRED 등 요구사항 ID 체계)를 직접 작성하지 않고 제공받은 문서를 읽고 이후 API 설계의 기준으로 삼았습니다. 각 일차 설계 문서(`docs/*_API_설계.md`)의 모든 엔드포인트가 이 요구사항 ID를 그대로 인용하고 있어, 설계 단계 전체가 이 문서 위에서 진행되었음을 확인할 수 있습니다. 다음 파이널 프로젝트부터는 이 요구사항 정의서 자체를 팀이 직접 작성해야 합니다.

### 3. API 명세서 작성

도메인별로 설계 문서를 먼저 작성한 뒤 구현에 들어갔습니다.

- [`docs/4일차_USER_API_설계.md`](docs/4일차_USER_API_설계.md) — 회원가입/로그인/JWT 인증/권한(Role) 정책
- [`docs/5일차_환자관리_API_설계.md`](docs/5일차_환자관리_API_설계.md) — 환자/진료기록 CRUD, 파일 업로드
- [`docs/6일차_폐렴예측_API_설계.md`](docs/6일차_폐렴예측_API_설계.md) — AI 예측 API, 캐싱 정책, 모델 평가 기준(Recall≥0.90)
- [`docs/9일차_동시성문제_해결을위한_아키텍처설계.md`](docs/9일차_동시성문제_해결을위한_아키텍처설계.md) — Redis 기반 이벤트 드리븐 아키텍처

설계 문서를 프론트엔드 코드(`static/apis.js`, `static/pages.js`)와 실제 DB 모델(`app/models/`)에 맞춰 작성했음에도, [`docs/7일차_앱_실행화면.md`](docs/7일차_앱_실행화면.md)에 정리했듯 실제로 화면에서 눌러보기 전까지는 발견되지 않는 계약 불일치(enum 대소문자, 필드 누락 등)가 여럿 있었습니다. **설계 문서는 구현의 출발점일 뿐, 실제로 연결해서 검증하는 단계가 반드시 필요하다**는 걸 확인한 과정이었습니다.

### 4. Git & GitHub Branch 전략 구성

[`docs/2일차_git_branch_전략.md`](docs/2일차_git_branch_전략.md)에서 Git Flow와 GitHub Flow를 비교 검토한 뒤, 브랜치 구조를 단순하게 유지하고 빠르게 리뷰·병합할 수 있는 **GitHub Flow**를 팀 전략으로 채택했습니다. 다만 브랜치 전략에 대한 합의가 "코딩 시작 전 담당자/진행 상황을 확인하는 절차"까지 포함하지 못해, 같은 기능에 대해 여러 브랜치·PR이 동시에 열리는 일이 반복됐고, 이후 `integration/*` 브랜치로 여러 구현을 하나로 정리하는 방식으로 대응했습니다.

### 5. 프로젝트 세팅

템플릿 저장소를 팀 레포로 전환하고, [`docs/3일차_프로젝트_뜯어보기.md`](docs/3일차_프로젝트_뜯어보기.md)에서 `app/core` → `models` → `repositories` → `schemas` → `services` → `apis`로 이어지는 계층형 구조를 정리했습니다. ERD를 기준으로 SQLAlchemy 모델을 작성하고 Alembic으로 마이그레이션했습니다([`docs/3일차_db_migration.md`](docs/3일차_db_migration.md)).

### 6. API 및 AI 워커 코드 작성 후 Branch 전략을 통한 코드 병합

- User API(인증/권한) → 환자관리·진료기록 API → 폐렴 예측 API/AI 워커 순으로 도메인을 넓혀가며 구현했습니다.
- 3~5일차에 여러 팀원이 같은 도메인을 독립적으로 구현하는 일이 있었고, User API는 최종 구현 브랜치를 그대로 채택, 환자/진료기록 API는 각자 만든 구현을 `integration/stage5-app-apis` 브랜치로 모아 하나로 정리하는 방식으로 병합했습니다.
- 이 과정에서 겪은 "같은 걸 여러 번 만드는" 비효율을 계기로, 이후에는 도메인 단위로 담당자를 정하고 작업 시작 전 열린 PR 목록을 먼저 확인하는 방식으로 개선했습니다.

### 7. 아키텍처 설계 및 적용

9일차에 FastAPI가 AI 추론까지 직접 처리할 때 생기는 동시성 문제(응답 지연, 중복 추론, 장애 추적 어려움)를 분석하고 Redis 대기열 + AI Worker 분리 구조를 설계했습니다. 10일차에 이를 실제로 구현하면서, 설계 문서가 제안한 "작업 등록 후 폴링으로 상태 조회" 방식 대신 **기존 프론트엔드 계약(예측 요청 시 결과를 즉시 응답)을 유지하기 위해 pub/sub 기반으로 결과를 동기 대기하는 방식**으로 조정해서 구현했습니다 — 설계와 구현 사이에서 기존 계약을 지키는 실용적 절충이 필요했던 지점입니다. 또한 실제로 로컬에서 돌려보는 과정에서 Redis 클라이언트 라이브러리의 두 가지 알려진 동작(구독 확인 메시지로 인한 타임아웃 미작동, 블로킹 명령의 소켓 레벨 타임아웃 레이스 컨디션)을 발견해 수정했습니다. 이론적으로 맞는 설계도 실제로 실행해보지 않으면 잡을 수 없는 문제가 있다는 걸 확인했습니다.

### 8. 도커 인프라 관련 파일 작성

`app/Dockerfile`과 `docker-compose.yml`(FastAPI + MySQL)을 먼저 작성했고, 한 차례 되돌리고(`revert`) 다시 작업하는 과정을 거쳐 정리했습니다. AI 워커 분리 이후에는 `worker/Dockerfile`을 추가하고, `pyproject.toml`의 의존성을 `torch`/`numpy`/`pillow`(AI 전용, `optional-dependencies`)와 기본 의존성으로 나눠 FastAPI 이미지 용량을 줄였습니다. `docker-compose.yml`에는 `mysql`, `redis`, `fastapi`, `ai-worker` 4개 서비스가 구성되어 있습니다.

### 9. AWS 배포 — 예정

아직 실제로 진행하지 않았습니다. 계획은 EC2(프리티어) 인스턴스에 Docker/Docker Compose를 설치하고, `docker-compose.prod.yml` + Nginx 리버스 프록시 구성으로 이미지를 배포하는 방식입니다. 다음 단계로 진행할 예정입니다.

### 10. QA 진행 — 예정

별도의 QA 단계는 아직 정식으로 진행하지 않았습니다. 다만 7일차 프론트-API 연동 검증과 9~10일차 로컬 실행 검증(정상/예외 케이스, 동시 요청, 장애 복구 시나리오 확인)이 QA의 초기 형태로 이루어졌고, 이를 바탕으로 전체 API에 대한 체계적인 QA를 진행할 예정입니다.

## 이 과정을 통해 배운 것

- 설계 문서와 브랜치 전략이 있어도, **담당자를 명확히 정하고 작업 전에 확인하는 절차**가 없으면 같은 작업이 반복된다.
- API 계약(요청/응답 형식)은 문서보다 **실제 프론트엔드 코드와 맞춰보는 것**이 최종 기준이다.
- 아키텍처를 아무리 잘 설계해도, **실제로 돌려보기 전까지는 검증되지 않은 설계**다.
- 이 네 가지는 다음 파이널 프로젝트에서 요구사항 정의부터 직접 해봐야 하는 이유이기도 합니다.

## Alembic Migration Guide

이 프로젝트는 데이터베이스 마이그레이션을 위해 Alembic을 사용합니다.

### 1. 마이그레이션 파일 생성 (자동 생성)
모델(`app/models/`)이 변경된 경우 다음 명령어를 실행하여 마이그레이션 파일을 생성합니다.
```bash
uv run alembic revision --autogenerate -m "변경 내용 설명"
```

### 2. 데이터베이스에 반영
생성된 마이그레이션을 데이터베이스에 적용하려면 다음 명령어를 실행합니다.
```bash
uv run alembic upgrade head
```

### 3. 이전 상태로 되돌리기 (Rollback)
마지막 마이그레이션을 취소하려면 다음 명령어를 실행합니다.
```bash
uv run alembic downgrade -1
```
